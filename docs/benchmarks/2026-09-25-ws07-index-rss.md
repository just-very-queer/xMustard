# WS-07 code index worker: peak RSS and incremental cost — 2026-09-25

Status: **measured.** `xmustard-core index build` indexes every eligible file of both
Apache/MIT fixtures under the 25 MiB heavy-slot line, with no file cap. A one-file
update takes 0.1 s. These are single-machine results under shared load, not a
universal ceiling.

## Setup

- Binary: `rust-core/target/release/xmustard-core` built from `parity/ws-07` at 2fbf234.
- Machine: Apple M1, 8 CPUs, 8 GB, macOS 27.0. Other agents shared the machine, with
  a load average of 8–15 during these runs.
- Driver: `scripts/bench/index-rss.sh <bin> <repo> <work> 3`. It clones the fixture into
  the work directory and keeps the index there, outside the fixture's `.git`. It runs
  three cold full builds (`--no-cache`), appends one function to the first tracked
  `.ts` file, and then runs `index update` twice: the incremental update, then a noop.
- Metric: `/usr/bin/time -l` maximum resident set size (ps-RSS, the gate basis) and the
  macOS peak physical footprint. The reported maximum also covers waited-for children,
  so Git children count; that is how the `git diff-files` spike below showed up.
- Fixtures: `research/cline` at ee59f81 and `research/pi-mono` at 5fd446c (Apache-2.0
  and MIT; GitNexus is not used, per §2.4), plus this worktree.

Raw records: `docs/benchmarks/evidence/2026-09-25/ws07-index-rss.jsonl`.

## What set the peak, and what was changed

These measurements drove the defaults in the committed code:

| Change | Effect measured on cline |
|---|---|
| Drop `git diff-files` and keep our own stat key per file. On smudged or racily clean index entries, `diff-files` re-reads every file. | The Git child alone measured **33 MB RSS / 24 MB footprint** on a fresh clone. It is no longer spawned. |
| Lexical fallback patterns: byte regexes with ASCII classes and a 64 KiB lazy-DFA cache. | Footprint after extracting one 160 KB file fell from 6.7 to 4.4 MiB. Unicode `\s`/`\w` classes had compiled to large automata. |
| FTS5 `hashsize` from 1 MiB to 256 KiB; bulk page cache from 2 MiB to 512 KiB. | Footprint fell about 2–4 MiB; there was no measurable slowdown. |
| Parse cap `max_parse_bytes` from 128 to 64 KiB. | Peak RSS went from 24.5–25.8 to 22.7–24.9 MiB. The largest parsed tree sets the transient: 4.5 MiB of footprint for one 95 KB TypeScript file. |
| Name-id cache from 32 Ki to 4 Ki entries; one parser per file; compact binary fact cache and clustered `refs`/`imports` tables. | A small, steady reduction in RSS; the cline index shrank from 107 to 80 MB on disk. |

What remains:

- About 7–8 MiB of the RSS is the binary's own text: code plus grammar tables for the
  touched languages.
- About 12–13 MiB is heap footprint. Allocator fragmentation dominates it; `vmmap`
  showed a live heap of 3–5 MiB with 59–78% fragmentation.

## Caveats

- These are single-machine results on macOS. Linux glibc arenas are not measured here.
  Gate v2 (WS-10) must repeat this on Linux.
- Grammar files above 64 KiB lose nested qualified names and tree-accurate references.
  They get lexical symbols and comment/string-stripped words instead, and each one is
  reported as `lexical_fallback`. Raising `--max-parse-bytes` costs about 30 bytes of
  parse tree per source byte.
- The index is about 80 MB on disk for cline, most of it references. Disk is not the
  gate.
