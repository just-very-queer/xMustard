# WS-15 watcher, refresh loop and identity unification — 2026-09-28

Status: **measured on Linux (the borrowed build box: 6 cores, 22 GB, glibc, inotify)
and on macOS (Apple M1, 8 GB, FSEvents).** An edit reaches the resident index in about
half a second on a 5,000-file tree, through the whole loop. ground's change tracking no
longer reads file contents on an unchanged tree. The watcher's memory is recorded under
"Gate v2" below.

## What is measured

- **Freshness.** This is the time from writing a file to the index generation that holds
  it. It covers event delivery, the 300 ms debounce, the cookie sync, the Go
  orchestrator's `watch take`, the one-shot `index update --paths <file>` in the heavy
  slot, `watch done` and the snapshot reload.
- **ground's change tracking.** `changetrack drift` (ground's drift section) and
  `changetrack working-changes` (its changed files), run one-shot, base core against
  head core.
- **Memory.** Gate v2 with the resident worker on (`--core-worker`, new in this
  workstream). Base is feat/parity-v2 at 3ab0b17 and head is parity/ws-15.

## Freshness on a 5,000-file tree

The fixture is the synthetic Go/Rust/TS/JS/TSX tree of `tests/refresh.rs`: 5,000 files
in 50 directories. Each edit rewrites one JS file and adds a function. Ten edits per run,
each 0.5 s after the previous one had landed.

| Path | Platform | p50 | max |
|---|---|---|---|
| In-process loop (`tests/refresh.rs fresh_within_a_second_on_5000_files`, `--release -- --ignored`) | Linux, inotify (57 directory watches) | 424 ms | 447 ms |
| In-process loop, same test | macOS, FSEvents | 488 ms | 504 ms |
| Through the API: worker on, one-shot `index update` in the heavy slot, freshness read with one-shot `index stats` | Linux, inotify | 497 ms | 549 ms |

- Through the API, `index update --paths <the file>` started 340 to 397 ms after the
  write: the debounce, the event latency, `CurrentRepoIdentity` and the take. The update
  ran 115 to 144 ms: scan 15 to 28 ms, edges 7 to 13 ms, graph segment 67 to 75 ms.
- Each update reparsed 1 file and re-resolved 1. The search that followed hit the new
  symbol from `resident_index`, and no core ran during that read.
- The in-process runs start the watcher on a built index. The start-up full refresh is a
  no-op update: 378 ms to `ok` on Linux, 560 ms on macOS.
- The API row's script is `evidence/2026-09-28/ws15-e2e-fresh.py`. It builds the same
  tree, starts the API with `XMUSTARD_CORE_WORKER=1`, registers the root with a first
  search (a full build of the 5,000 files: 11.7 s to `ok`) and waits for
  `watcher_state: ok`. It never reads through the API between an edit and its
  generation change. The raw output of all three rows is in
  `evidence/2026-09-28/ws15-freshness.txt`.

## Git in each refresh batch (Linux, one-shot)

PAR-FRESH-03 asks that Git run only on overflow or a HEAD or Git index change. Queries
meet that under the watcher, but each refresh batch does not: its one-shot
`index update --paths` scans the tree, and the scan lists it with `git ls-files -s` and
stats every tracked file. So a batch spawns Git and costs time in proportion to the
tracked-file count. Measured with one edited file per update, five updates per tree:

| Tracked files | scan | whole update | `git ls-files -s` alone |
|---|---|---|---|
| 5,000 | 16-23 ms | 68-80 ms | 4 ms |
| 20,000 | 49-52 ms | 149-154 ms | 7 ms |
| 50,000 | 114-153 ms | 219-279 ms | 17 ms |

- The listing itself is a small part; the per-file stat is most of the scan. At 50,000
  files a batch still lands well inside the 1 s freshness target (300 ms debounce plus
  about 250 ms of update).
- Script and raw output: `evidence/2026-09-28/ws15-scan-cost.sh` and
  `ws15-scan-cost-linux.txt`. The plan records this as a WS-15 deviation.

## ground's change tracking (Linux, one-shot)

Setup:
- Each tree is a private clone of the pinned fixture. Its index was settled once, as the
  user's own Git commands would settle it. A fresh clone is racily clean, and
  `--no-optional-locks` cannot refresh it, so `git status` would take 0.56 s on it.
- Each core built its own baseline.
- Load average was 0.8 to 1.4.
- Script and raw output: `evidence/2026-09-28/ws15-ground-cost.{sh,txt}`.

Drift per call, in ms. "Warm" is five calls; "no stat cache" is one call after the
tracked-file stat cache was deleted.

| Tree | Tracked files, bytes | `git status` alone | base, no stat cache | base, warm | head, warm | head `drift_checked` |
|---|---|---|---|---|---|---|
| pi-mono (`5fd446c`) | 1,929, 25.1 MB | 9 | 57 | 32-35 | 18-25 | `identity`, hashed 0, compared 0 |
| parity composite (cline + pi-mono + OpenHands) | 7,288, 85.4 MB | 18 | 164 | 104-109 | 42-46 | `identity`, hashed 0, compared 0 |

- **Base drift** lists every tracked file (`git ls-files`), stats each one and reads each
  one whose stat entry is missing or changed. Its cost therefore follows the tracked
  file count, and the tracked bytes whenever the stat cache is cold.
- **Head drift** reads the observation the source identity makes (`git status`, HEAD,
  branch, origin). When HEAD equals the baseline's, it compares only the paths
  `git status` lists, plus those an explicit baseline took in. It hashes nothing on a
  clean tree, whatever the tree's size. What remains is `git status` and reading the
  4.8 MB baseline.
- **Dirty tree** (three edited tracked files, one untracked file):
  - Base: 163 ms on the first call, then 101-103 ms.
  - Head: its first call hashed the 4 files; later calls stat-skipped them (hashed 0,
    stat_skipped 4, compared 3), at 43-45 ms.
- **working-changes** is 3-4 ms slower on head (41-43 ms against 36-39 ms on the
  composite). It now runs the whole source identity (status, branch, origin) instead of
  a bare `git status`, and shares that observation with drift under the watcher.
- **Inside `serve`, with the watcher `ok`, ground spawns no Git and reads nothing.**
  drift answers from the watcher's last observation of the root
  (`drift_checked.mode: "watcher"`) until any event arrives under the root.
  `tests/refresh.rs ground_on_an_unchanged_tree_hashes_nothing` asserts zero Git spawns
  for drift and working changes under the watcher.
- **The 14.8 s PAR-FRESH-01 figure** was ground on the gitnexus clone, taken before
  w0-drift's stat cache existed. GitNexus is PolyForm Noncommercial and is not used as a
  fixture or comparator (§12.3), so the Apache/MIT composite stands in for it.

## Gate v2 (Linux, `--core-worker`, three runs per scenario)

Base is feat/parity-v2 at 3ab0b17 and head is parity/ws-15, both with the resident
worker on and the parity composite. `--workstream WS-15` compares them on `agents-2`,
the ledger's designated scenario. Reports: `evidence/2026-09-28/ws15-gate-v2-parity-{base,head}.md`.

| Scenario | base gate peaks (MiB) | head gate peaks | `rust_index_service` RSS p50 / PSS p50, base → head | its peak, base → head | watcher marker, head |
|---|---|---|---|---|---|
| agents-2 | 200.9, 204.6, 209.1 (FAIL) | 201.3, 201.3, 208.6 (FAIL) | 11.2 / 4.9 → 9.3 / 4.8 | 171.7 → 171.7 | on (`overflow` first seen) |
| snapshot-swap-under-load (edits, no watcher at base) | 215.7, 217.4, 305.5 (INVALID: no swap under load) | 217.9, 218.1, 258.6 (FAIL; 2 of 3 runs did not swap under load) | 21.5 / 16.3 → 18.5 / 13.7 | 184.7 → 185.3 | `ok` |
| watcher-on | skipped (no watcher) | 215.9, 217.9, 223.3 (FAIL) | — → 18.0 / 13.2 | — → 185.0 | `ok` |

- **The WS-15 line (2 MiB on `rust_index_service`)** is within resolution, and the
  ledger check reports `BELOW_RESOLUTION`: the line is under the 3 MiB process
  tolerance. The measured deltas are negative:
  - agents-2: `rust_index_service` PSS p50 -0.1 MiB, RSS p50 -1.4 MiB; the owned tree
    -3.3 MiB.
  - With edits under load: the service's p50 is 18.0-18.5 MiB with the watcher, against
    21.5 MiB at base without it.
  The watcher's own state is small next to the service's p50: queue, layout, ignored
  directories and one repository observation. Its inotify watches are kernel memory.
- **The gate fails on both sides for a reason outside WS-15.** In every run the resident
  worker peaks at 171-185 MiB, almost all of it anonymous memory (157-182 MiB at the
  peak sample). That peak is the same at base and head. It is consistent with WS-14's
  fallback, the ledger's WS-14 open item: while the index lags the reads' identity (its
  first build, and between edits), the worker builds the legacy graph of the 7,288-file
  tree in process. With the worker off, the same scenarios run per-call cores, and WS-14
  measured agents-2 at 94.0 MiB.
- **The swap under load now happens.** At base no run advanced `snapshot_generation`
  while the agents queried (INVALID). With the watcher, the first head run swapped in all
  three repeats (generations 1 to 4); the second in one of three. The heavy slot still
  refuses refreshes while the tree is over the soft ceiling, which the worker's peak
  causes.
- **Worker recycles.** The governor replaces the worker above its lines. Scenarios saw
  up to eight worker processes at head in the first run, and four at base. The watchers
  went with each worker. Some reads then reported
  `watcher_state: absent`, and the watcher marker was off in two scenarios
  (`ws15-gate-v2-parity-head-before-rewatch.md`). A replacement worker now registers its
  predecessor's roots before it takes a call. In the rerun reported above, the marker
  was `ok` in both edit scenarios.
