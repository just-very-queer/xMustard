# Competitor parity for xMustard — 2026-09-24

Research snapshot: 2026-09-24, approximately 08:15–08:30 UTC. Product direction confirmed during this review: **shared, verified memory and repo intelligence for existing coding agents**. UI work and replacing the agent are outside this comparison.

## Conclusion

xMustard has a relevant product thesis, but search, symbol graphs, MCP access, shared memory, and provenance are already offered by several peers. The candidate distinction is their combination: a small, agent-independent interface to repository facts whose promotion, supporting evidence, freshness, and conflicting claims are inspectable. That distinction is a hypothesis to validate against real tasks, not proof of superiority.

The seven families below cover the requested code-context and agent-memory competitors. GitNexus, Serena, Augment, and Sourcegraph are direct comparisons for repo intelligence. Mem0 and Zep/Graphiti are direct comparisons for memory infrastructure. Letta is an adjacent runtime whose memory mechanisms are relevant; its full agent product is not a parity requirement.

Method: live official documentation, official repositories, and GitHub REST metadata. No competitor was installed or benchmarked in this review. “Documented” means a first-party description or source was inspected; it does not establish runtime correctness. “Not found” means not established in the listed sources, not that the feature cannot exist. No peer's reviewed documentation established the exact xMustard combination of distinct-principal memory approval and repository-file hash checks on recall; that limited finding is not a market-wide uniqueness claim.

Recommended parity sequence for the confirmed product direction:

1. **Reliable consumption:** a clean source install, stable data location, clear optional dependencies, repeatable MCP registration, cancellation, and workspace-scoped identity. This makes comparisons reproducible.
2. **Verified memory:** publish precise state transitions and evidence receipts; test stale, rejected, superseded, and conflicting memories during multi-agent handoffs. Treat verifier independence as a measurable limitation.
3. **Repo intelligence:** establish honest language coverage and freshness first, then measure retrieval and impact against GitNexus/Serena or an available service using the same repository/task subset.
4. **Measured benefit:** run memory-off, ungoverned-memory, governed-without-drift, and governed-with-drift arms under fixed model, budget, tools, seeds, and task scoring. Record accepted patches, localization recall, tokens, wall time, stale-memory harm, incorrect promotions, and handoff success. Add one relevant competitor arm at a time.

These are proposed acceptance categories, not an approved implementation backlog or a commitment to copy every competitor feature. Numeric thresholds, the first supported language/repository set, and whether larger search services should be integrated remain product choices.

## Relationship to the project's earlier direction

[RETHINK.md](../RETHINK.md) already identifies grounding and governed memory as the central product and treats broad runtime/platform functions as secondary. That remains compatible with the user's confirmed direction. Its claim that static indexing is generally dead weight should not be treated as settled research: the current peer sources above use indexes, live language services, or both. The decision to keep or replace an index should follow freshness, retrieval-quality, latency, and resource measurements for xMustard's workloads.

The existing nine-tool surface is a useful scope boundary, but neither nine tools nor a governance label proves better outcomes. The immediate opportunity is to make trusted, current context easy for existing agents to consume and to publish evidence showing where that changes results.

## Research limits

- This is a dated survey of seven requested families, not an exhaustive market search or an installation audit of those products.
- Capability rows describe current docs/main unless a release is explicitly named; they do not backport new features into older releases.
- Hosted proprietary internals, exact deployed versions, undocumented governance, and equal-hardware resource measurements were not established.
- No third-party summaries were used as evidence. Vendor benchmark claims are labelled, and no paid services or external agent runs were started.
