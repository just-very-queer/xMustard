## Prioritized findings

### 1. Plain `recall` bypasses the bounded recall implementation

**Priority: high for the core product. Evidence: confirmed source control flow.**

The MCP description promises recency-ranked top-N when no query is supplied, but the [HTTP handler](../../api-go/cmd/xmustard-api/main.go#L3223) calls `RecallContext` only when `query` or `paths` is nonempty. Plain `recall` goes to `GetActiveContext`, which [loads every promoted entry and hashes every referenced path](../../api-go/internal/workspaceops/context_governance.go#L714). The bounded default and candidate window in `RecallContext` are therefore unused by the normal no-argument call.

The result can grow with the entire memory history, overwhelm the agent context, and eventually exceed the MCP proxy's [16 MiB response cap](../../api-go/cmd/xmustard-mcp/main.go#L235). This contradicts the documented bounded retrieval behavior even though the bounded function's unit tests pass. Route plain recall through the bounded implementation; keep any full-history administrative view separately explicit.

### 2. API main does not wait for graceful shutdown to finish

**Priority: high for durable runs and process lifecycle. Evidence: confirmed source control flow.**

The [signal goroutine](../../api-go/cmd/xmustard-api/main.go#L3783) calls `srv.Shutdown`, then attempts to interrupt runs, close terminals, and flush PostgreSQL. However, [main returns after `ListenAndServe` reports `http.ErrServerClosed`](../../api-go/cmd/xmustard-api/main.go#L3806); it never waits for that goroutine. Closing the listener makes `ListenAndServe` return before HTTP drain and subsequent cleanup necessarily finish.

Consequently the intended [durable interrupted-state and child-process cleanup](../../api-go/internal/workspaceops/shutdown.go#L18) can be cut short by process exit. Add an explicit completion join owned by main and a process-level shutdown test with an in-flight fixture. Existing shutdown helper behavior alone does not establish server shutdown correctness.

### 3. Non-loopback startup can pass the auth interlock with auth disabled

**Priority: high for operators exposing the API. Evidence: confirmed condition mismatch; not exercised against an exposed listener.**

The [non-loopback check](../../api-go/cmd/xmustard-api/main.go#L3737) rejects startup only when auth mode is not `required` **and** no tokens are configured. Therefore `XMUSTARD_AUTH=off` passes whenever a token store or environment token exists. The later [middleware setup](../../api-go/cmd/xmustard-api/main.go#L3753) skips authentication entirely for `off`.

With TLS configured, or with the separately supported insecure-bind override, this exposes ordinary workspace and provider routes without authentication despite the startup comment promising an auth requirement. The loopback default limits the default exposure; this finding concerns the explicitly supported remote-bind configuration. Require an enforcing auth mode for non-loopback startup and test the complete configuration matrix.

### 4. MCP cancellation does not propagate through the core HTTP handlers to Rust

**Priority: medium. Evidence: confirmed source call chain.**

The MCP proxy attaches a context to its HTTP request, but core handlers such as [search](../../api-go/cmd/xmustard-api/main.go#L3340), [impact](../../api-go/cmd/xmustard-api/main.go#L3177), and [ground](../../api-go/cmd/xmustard-api/main.go#L3480) do not forward `r.Context()` into their workspace operations. Their bridge ultimately calls [runCoreContext with `context.Background()`](../../api-go/internal/rustcore/root.go#L52).

Cancelling an MCP request therefore disconnects the HTTP client while backend work can continue until its own deadline. The MCP HTTP timeout is 60 seconds and the generic core timeout is 120 seconds. The [transport comment claiming whole-chain teardown](../../api-go/cmd/xmustard-mcp/main.go#L191) overstates what is wired. Thread caller contexts through the nine-tool paths and verify cancellation with a real child-process fixture.

### 5. The shared transient budget is accounting, not a process-memory ceiling

**Priority: medium; blocks strict resource-bound claims. Evidence: confirmed source admission paths.**

`ByteBudget.Acquire` can reject excess reservations, but [Charge intentionally permits usage beyond the maximum](../../api-go/internal/budget/budget.go#L47). `runBoundedCmd` charges a 64 MiB stdout reservation plus stderr unconditionally. The more commonly used [runCoreCtx does not charge the budget at all](../../api-go/internal/rustcore/root.go#L58), despite capturing up to 64 MiB per invocation.

The HTTP [budget check applies only to sufficiently large or chunked request bodies](../../api-go/cmd/xmustard-api/main.go#L3971). Small requests and GET tool calls can still initiate concurrent allocations and subprocess work; the MCP reader also [starts a goroutine for each request without an admission limit](../../api-go/cmd/xmustard-mcp/main.go#L538). Per-call caps do not establish an aggregate 50–100 MB bound. Add enforced work/concurrency admission and measure the complete process tree before asserting a hard resource ceiling.

## Additional trust-consistency concern

**Source-inferred concurrency issue; no dedicated interleaving reproduction was run.**

Ranked recall [captures promoted metadata and a content hash](../../api-go/internal/workspaceops/context_governance.go#L754), then loads content later. A concurrent [readwrite-content update](../../api-go/internal/workspaceops/context_governance.go#L658) resets approvals and promotion, writes the new text, and [prunes the old hash file](../../api-go/internal/workspaceops/context_governance.go#L303). If recall now misses its old hash file, [loadWindowContent falls back to current source content by entry ID](../../api-go/internal/workspaceops/context_governance.go#L346), without checking that content's hash/version against the captured promoted metadata. [Recall attaches that text to the old metadata](../../api-go/internal/workspaceops/context_governance.go#L898).

That interleaving appears able to return newly unverified text with an older verified status and approval list. Existing content-store tests cover pruning and fallback independently, not their interaction with an in-flight recall. Reproduce deterministically before designing the fix; require metadata and content from the same verified version, or retry the read when their versions differ.

## Organization implications

The Go backend is much broader than a thin HTTP shell: `workspaceops` has 257 exported function declarations across its files, while `cmd/xmustard-api/main.go` alone has 4,180 lines. A directory move would not resolve its shared state or route-policy coupling. Organize documentation around four real ownership areas first: core governed memory and retrieval; optional issue/run cockpit; persistence and process lifecycle; transport and authorization.

Future code decomposition should follow those boundaries with regression protection for route contracts, verified-memory versions, shutdown completion, and cancellation. Keep the nine MCP names stable. Preserve explicit distinctions between implementation, unit-test evidence, live integration evidence, and product-value experiments.
