# xMustard v0.1.1

Released 2026-09-28. The second tagged release: `feat/parity-v2` at `1c64982`, with the
v0.1.0 docs refresh from `main` merged in, on `release/v0.1.1`. It fixes the two
release-affecting bugs of [v0.1.0](v0.1.0.md) and adds the Claude Code plugin, the
index watcher, a background service with store backup, file-level `impact` and a
tag-triggered release workflow. Each workstream's implementation record in the
[parity build plan](../plans/2026-09-25-parity-build-plan.md) holds its details,
checks and deviations.

**This is not a parity claim.** Numeric parity thresholds and the final parity-scale
gate arrive with WS-50, and the parity-scale suite (4 agents, 2 hot repos, 4
worktrees) still exceeds its 95.4 MiB line.

## Fixed

- **Evidence capture works, and every capture is redacted** (WS-FIX-03). In v0.1.0 no
  production build wired a secret redactor into capture, so
  `POST /api/workspaces/{id}/evidence/capture` answered `503 redaction_unavailable` to
  every request: the Pi adapter's built-in tool reduction, masking and compaction fell
  back to Pi's own behavior, and no hook body could be captured. Now capture is on in
  every build, and the tool output streams through the shared secret rules before any
  of it reaches the spool, so the retained original, its pages, search inside it and
  the projection all hold `[REDACTED:<rule>]` in place of each secret.
  [Details below](#capture-redaction).
- **Drift is checked at every path depth.** In v0.1.0 a memory anchored to a file at
  an even path depth, such as `pkg/auth.go`, was baselined as missing and never flagged
  stale when the file changed. The confined file walk compared its final descriptor
  with the root's closed descriptor number, which the OS reuses. It now tracks whether
  it opened a component (`7d380c4`, `TestConfinedReadOfEveryDepth`). The evaluation
  corpus separates the bug from the fix: in its fake-driver dry run, recall flagged
  neither of its two even-depth stale memories before the fix and both after it. A
  memory promoted under v0.1.0 at an even depth kept a missing baseline for that file;
  see [Upgrading](#upgrading).
- **Argument errors reach the agent** (WS-FIX-05). A call with an argument the tool
  does not take came back as a JSON-RPC `-32602` error with no result content, which
  clients showed as "Empty response". An agent that called `impact(path=...)` concluded
  that the index or Postgres was missing. Argument errors are now tool results the
  agent can read ([below](#changed-behavior)).
- **Client adapter corrections** (WS-FIX-04). `client=claude-code` on the capture route
  silently got the generic envelope instead of Claude's shapes; it is now an alias of
  `claude`. An `"error": null` member no longer marks a hook body failed. An output
  with image blocks is no longer replaced by a text-only payload that silently dropped
  them; the client keeps its own. The Codex hook fields Codex never sends (`call_id`,
  `error`) are no longer read, and `turn_id`, `agent_id` and `transcript_path` are. The Pi adapter sends recall's MCP default
  (`max_chars=4000`), so Pi and MCP clients issue the same request.
- **A SIGTERM during start-up no longer skips the drain** (WS-58). The API installs its
  signal handler before it serves; a signal that arrived after the API answered but
  before the handler ran used to kill it without the 25 s drain.

## New

### Claude Code plugin and hook service (WS-23)

`integrations/claude-code` is a Claude Code plugin: the nine tools over `/mcp`, plus
hooks that post Claude Code's events to the daemon (`POST /api/hooks/claude/<Event>`,
15 events).

- `PostToolUse` on Bash, Read, Grep, Glob, WebFetch and other servers' MCP tools
  captures the output (redacted), reduces it by tool family and returns it as
  `updatedToolOutput` when the reduction matches the tool's output shape; its last line
  names the recovery handle. A test, build or lint output becomes a run outcome that
  `ground` lists.
- `PreToolUse` on Grep, Glob and Bash `rg`/`grep` adds up to five index hits and the
  memories recall ranks for the pattern; on Read and Edit, the memories bound to the
  file, stale ones labeled. After an edit it reports the tree-sitter syntax errors the
  edit introduced.
- `SessionStart` and `SubagentStart` add ground's spawn-free summary and the core-tier
  memories. `UserPromptSubmit` pushes the memories a prompt keyword triggers (tag
  `trigger-<keyword>`). `FileChanged` and edits feed the index watcher.
- Pushed memory is only memory a human approver approved, that is not quarantined and
  that scans clean, framed as data. Each context (the main thread, each subagent) gets
  a memory at most once until compaction.
- No hook allows, denies or rewrites a tool call. An answer past the ~200 ms budget is
  an empty 200, so Claude Code keeps its own behavior; authentication still fails
  closed (401/403, shown as a non-blocking hook error). The daemon starts no process
  for a hook. Claude Code starts the static client `xmustard-hook` for the two command
  hooks, SessionStart and WorktreeRemove; it talks to the daemon over a Unix socket
  that must be private to the user, else over TCP.

Measured on the Linux build box (Ryzen 5 3500X), `scripts/bench/hooks-load.py` against
the built daemon, 600 calls of each from 4 concurrent clients: PreToolUse(Read) p50
4.2 ms, p95 7.5 ms; PostToolUse(Bash, a 30,000-character output) p50 4.0 ms, p95
8.5 ms, 600 of 600 outputs replaced; 0 process spawns; API RSS 27.7 MiB before and
35.8 MiB after, peak 41.7 MiB. `xmustard-hook` is a 3.5 MB binary that peaked at
4.8 MiB RSS (median of 20 SessionStart runs) and ran in under 10 ms.

Install steps: [integrations/claude-code/README.md](../../integrations/claude-code/README.md).
The security model: [SECURITY.md, client hooks](../SECURITY.md#client-hooks-ws-23).

### Index watcher and incremental refresh (WS-15)

With the resident worker on (`XMUSTARD_CORE_WORKER=1`), the core watches each
registered repository (FSEvents on macOS, inotify on Linux, at most 4 roots) and the
API turns the debounced batches (300 ms, at most 1 s) into incremental index updates.
Overflow, an ignore-file change or an OS watch limit makes a full refresh; failures
retry with backoff and report `degraded`. The freshness envelope carries
`watcher_state` and the last run's counters, and while the watcher vouches for a root,
queries spawn no Git.

On a 5,000-file tree an edit reached the index in p50 424 ms (max 447) on Linux with
inotify and p50 488 ms (max 504) on an Apple M1 with FSEvents in the in-process loop
test, and in p50 497 ms (max 549) on Linux through the API
([WS-15 record](../benchmarks/2026-09-28-ws15-watcher.md)). ground's drift check now
compares only the paths `git status` lists when HEAD is at the baseline, so it hashes
no file on an unchanged tree: on a 7,288-file, 85 MB tree it took 42 to 46 ms against
104 to 109 ms in v0.1.0 (Linux, settled Git index).

### Background service and store backup (WS-58)

`xmustard-ops setup` installs the API as a per-user service and waits for
`/api/health`: a launchd agent on macOS (started at login, restarted after a crash) or
a systemd socket and service on Linux (socket-activated; connections made while it
restarts wait in the socket's backlog). The unit binds loopback only and carries no
token. `daemon status|restart|stop` and `uninstall` complete it. Rerunning setup after
an upgrade restarts the daemon on the new binaries.

The API now migrates the governance store and runs `PRAGMA quick_check` when it
starts, and reports the result as `store` on `/api/health`; a damaged store fails
memory calls closed until a backup is restored. `xmustard-ops store backup` writes a
verified `VACUUM INTO` copy beside a running daemon, `store check` checks a store or a
copy read-only, and `store restore` stops the daemon, swaps the store (keeping the old
one aside) and starts it again. `xmustard-relay` waits up to 10 s for a restarting API.
The daemon logs to a rotated file (10 MiB, 3 generations).

Measured on the Linux build box: the start-up check took 93 to 108 ms on a 12.4 MiB
store of 3,000 entries.

### File-level impact (WS-FIX-05)

`impact(path=<repo-relative file>, max_depth?)` returns the files that reference any
symbol defined in that file, up to 4 hops: `impact(symbol=)`'s walk, started from a
file. `found: false` says the graph does not hold the path. On a Git copy of
`api-go` (540 files), `impact(path="api-go/internal/govstore/entries.go")` answered 491
files at depth 4 (35 at distance 1) and 35 with `max_depth=1`. The graph is lexical,
so edges at distance 1 or more stay leads, not proof.

### Release workflow and packaging (WS-26)

- `.github/workflows/release.yml` builds the release on a `v*` tag push: `make release`
  on `ubuntu-22.04` (linux-x86_64) and `macos-15` (darwin-arm64), with pinned
  toolchains (Go 1.26.1, Rust 1.93.1), no build cache, and a check that each archive
  carries its platform's name. It then drafts a GitHub release with both archives,
  their `.sha256` files and `SHA256SUMS`, with these notes. The owner publishes the
  draft.
- `make release VERSION=vX.Y.Z` builds the same archive locally: build paths are
  remapped and archive metadata is fixed, so rebuilding a commit on the same runner
  image gives the same bytes. `make release-sums` checks the archives and writes
  `SHA256SUMS`.
- `packaging/homebrew/bump.sh <tag>` moves the Homebrew formula to a published release,
  taking each checksum from its `SHA256SUMS`.
- `.gitignore` ignores `backend/data/`; untracking the 80 runtime files already
  tracked there waits on the owner. WS-26 ran `gofmt` and `rustfmt` over the sources
  in formatting-only commits.

## Changed behavior

- **Argument errors are tool results.** Every argument validation failure (unknown
  argument, wrong type, out of range or enum, missing, conflicting alias) is a
  `tools/call` result with `isError: true`: the error, a `Hint:` line when a
  did-you-mean row applies (for example `explain(symbol=...)` points at `search` or
  `impact`), and the tool's arguments. `_meta["xmustard/argument_error"]` carries the
  same as data. This follows MCP 2025-11-25's error handling. The ground and recall
  budget rejections arrive this way over MCP too; over HTTP they stay 400.
- **An unknown tool is JSON-RPC `-32602`** (`Unknown tool: <name> (tools: ...)`), no
  longer an `isError` result. A malformed request stays `-32602`.
- **`tools/list` grew by 119 bytes** in every profile for `impact`'s `path` argument:
  8,888 bytes for all nine tools in the lean profile on protocol 2025-06-18.
- **Capture refuses more.** `422 secret_path` when any path the capture names is on the
  secret-path denylist (`.env`, SSH keys, `.netrc`, `.npmrc` and the like),
  `503 redaction_failed` when the redactor fails, and `400 invalid_client` for an
  unknown client. A retained original holds markers where secrets were, and the 16 MiB
  limit applies to the redacted bytes: 16 MiB of `secret=x` lines redacts to 55 MiB
  and is refused with `413`.
- **The governance store moves to schema version 3** the first time a v0.1.1 API or
  ops command opens it (the review subjects migration). v0.1.0 refuses to open a newer
  store, so going back needs a copy taken before the upgrade.
- **The API opens its store at start-up** to check it. With an existing store, idle
  RSS is about 5.5 MiB higher right after start (19.5 against 25.0 MiB on the build
  box), memory the first memory call loaded anyway.
- **`codex_args` is an allow-list.** The platform profile's Codex runs accept only
  `--ephemeral`, `--strict-config`, `--oss`, `--color` and `--local-provider` beyond
  the flags xMustard pins; anything else, `-p/--profile` included, is refused with 400.

## Capture redaction

- **Rules.** Capture uses the rules `why_failed` applies to command output: bearer and
  basic credentials; AWS, GitHub, GitLab, Slack, OpenAI, Anthropic, Google, Stripe,
  npm, Hugging Face and xMustard tokens; JWTs; URL passwords; private keys; secret
  fields in JSON, YAML, env files, headers and flags; and the literal values of the
  daemon's secret-named environment variables.
- **Streaming.** The redactor buffers 128 KiB and decides it 8 KiB at a time, reading
  each window with the 33 KiB lookahead after it, the longest span any rule reads. A
  secret split across writes is seen whole, and the stream is never buffered whole.
- **Secret paths.** Every path the capture names is checked: the caller's `path`, and
  every path field of the hook body's tool input and response. The client keeps its
  own result.
- **Fail closed.** A server without a redactor answers `503 redaction_unavailable`,
  and a redactor that fails answers `503 redaction_failed`. Nothing is retained either
  way.

Measured on the Linux build box (AMD Ryzen 5 3500X):

- `redact.Writer` alone (`BenchmarkWriter16MiB`, 32 KiB writes): 142 MB/s on a stream
  with a secret pair every 4 KiB and 33 MB/s on one that is nothing but secrets
  (`secret=x` lines), allocating 0.27 MB and 0.47 MB per 16 MiB.
- Peak live heap of the redactor over 16 MiB of one repeated unit
  (`redact.TestWriterMemoryIsBounded`): 0.17 to 0.37 MiB, the most for an 8-byte
  secret environment value repeated, under a quarter of the 2 MiB capture window.
- The capture route end to end against a real `xmustard-api`, range of three
  interleaved runs at a host load average of about 6 to 10 on 6 cores, against the
  same build with a pass-through redactor (a temporary build tag, not committed):

  | Workload | Redacted | Pass-through |
  |---|---|---|
  | 6 sequential raw 16 MiB captures, a secret pair every 4 KiB | 31.4 to 33.0 MB/s | 33.3 to 39.3 MB/s |
  | 4 sequential raw 4 MiB captures of nothing but secrets | 6.5 MB/s | 6.5 to 6.7 MB/s |
  | 200 Claude hook bodies of 256 KiB, 4 at a time | 40.1 to 44.1 MB/s | 46.8 to 48.9 MB/s |
  | API peak RSS (`VmHWM`) over the three workloads | 36.4 to 37.0 MiB | 44.2 to 44.8 MiB |

  Idle RSS was 18.7 to 19.0 MiB for both. The dense workload is bound by the shell
  reducer, not the redactor.

The rules and their limits: [SECURITY.md](../SECURITY.md#evidence-capture-redaction-ws-fix-03).

## Install

**Prebuilt binaries** for macOS arm64 and Linux x86_64 are attached to the release as
`xmustard-v0.1.1-<os>-<arch>.tar.gz`, each with a `.sha256` file, plus `SHA256SUMS`.
Each archive holds `xmustard-api`, `xmustard-ops`, `xmustard-relay`, `xmustard-core`,
`xmustard-mcp` and `LICENSE`. To install one:

1. Check the archive against its `.sha256` file.
2. Put the binaries on `PATH`, or point `XMUSTARD_CORE_BIN` at `xmustard-core`.
3. The macOS binaries carry only an ad-hoc signature, with no Developer ID. After a
   browser download, clear the quarantine flag:
   `xattr -d com.apple.quarantine xmustard-*`. `curl` does not set the flag.

These archives are the first built by the release workflow: linux-x86_64 on GitHub's
`ubuntu-22.04` image and darwin-arm64 on `macos-15`. The Rust binaries link the build
image's glibc, 2.35 on Ubuntu 22.04, so they need glibc 2.35 at most (Ubuntu 22.04 or
newer, Debian 12 or newer); the exact floor was not measured. v0.1.0's Linux binaries,
built on a newer system, needed 2.39. The Go binaries are static: they are built
without cgo, so the platform profile's PTY terminals are not available in them; build
from source for those.

**The Claude Code plugin** is not in the archive: its static hook client is built from
a source checkout with Go 1.26
([integrations/claude-code](../../integrations/claude-code/README.md)).

**From source** (Go 1.26, Rust stable): `make build`, or `make release` for the
archive.

**Homebrew**: `packaging/homebrew/xmustard.rb` pins v0.1.0 until the owner moves it to
this release with `sh packaging/homebrew/bump.sh v0.1.1`.

## Upgrading

1. **Keep a way back.** v0.1.1 migrates `governance.db` to schema version 3 when it
   first opens it, and v0.1.0 refuses a newer store. Before the first v0.1.1 start or
   any other v0.1.1 command, take a copy with the new `xmustard-ops store backup` (it
   reads without migrating, and works beside a running daemon); the copy stays at the
   old schema.
2. **Restart the API** on the new binaries, or run `xmustard-ops setup` to install it
   as a service. With the Claude Code plugin, set `XMUSTARD_CORE_WORKER=1`
   (`xmustard-ops setup --env XMUSTARD_CORE_WORKER=1`) so hooks can add index hits.
3. **Re-check even-depth memories.** A memory promoted under v0.1.0 and anchored to a
   file at an even path depth recorded that file as missing (`"\u0000missing"` in
   `path_hashes`). v0.1.1 reads the file, so recall flags the memory stale: the file
   "appeared". The baseline is taken once, at promotion, so check each such memory
   against its file and supersede it (the new entry records a fresh baseline when it
   is promoted) or retire it.
4. **Pi**: update the extension from the checkout. Against a v0.1.1 API its built-in
   reduction, masking and compaction work.
5. **Agents that parsed errors**: an argument error is now an `isError` result, not a
   JSON-RPC error; an unknown tool is now a JSON-RPC error.

## Known limits

- **Not a parity claim.** The parity-scale suite (4 agents, 2 hot repos, 4 worktrees)
  still exceeds its 95.4 MiB line. With the resident worker on, gate v2's parity
  composite peaked at 201 to 209 MiB for 2 agents, at the WS-15 base and head alike;
  the worker builds the legacy graph while the index lags the reads. On the evaluation
  corpus's real repositories (pi-mono, cline), the process tree peaked at 91.7 to
  120.9 MiB through the stdio shim, over the line in 5, 8 and 7 of 10 runs; that is a
  lead for WS-50, not a gate result.
- **The Pi adapter e2e passes in part: 9 of its 18 tests.** Its unit tests and the
  WS-24 suite (built-in tools through capture with secrets redacted, masking,
  compaction) pass. Nine tests of its first suite fail with or without this release's
  fixes: each needs a multi-page result from `impact` with no arguments, and since
  v0.1.0's automatic registration baseline the fixture repository has no changes
  against its baseline, so that call returns about 400 bytes and issues no handle. The
  fix is a large-result fixture, an open follow-up of the Pi adapter workstream
  (WS-24).
- **The resident worker is opt-in.** The watcher and the hooks' index hits and syntax
  report need `XMUSTARD_CORE_WORKER=1`. After the worker's 2-minute idle exit nothing
  is watched until the next call. Each refresh batch still runs `git ls-files -s` and
  stats every tracked file (16 to 23 ms at 5,000 files, 114 to 153 ms at 50,000).
- **Redaction is pattern-based.** A secret no rule knows is retained as written. Only
  named paths are matched: `cat .env` through a shell, or a search over a directory
  that matches a secret file, passes through the content rules only. A secret split
  across two output strings of one hook body is not joined. Revoke an original with
  `DELETE .../evidence/{handle}`.
- **Hooks.** Codex, OpenCode and Cursor still get MCP configuration only; their hook
  adapters are WS-40. The plugin's http hook URLs name `127.0.0.1:8042`, because Claude
  Code does not expand variables in a hook URL. With the daemon down, an http hook
  shows a non-blocking error notice. A static client that gives up in the last ~20 ms
  of its budget on a loaded host drops an answer the daemon counted as delivered, so
  those memories are not pushed again in that context until compaction.
- **Service.** launchd has no socket activation for the cgo-free API, so the macOS
  agent is resident from login and connections are refused while it restarts. A hung
  daemon is not detected (no watchdog). Restore is offline: it stops the daemon.
  `daemon status` under systemd starts the daemon. The real-launchd integration test
  was not run; the real-systemd one passed 8 of 9 runs, and the one failure (an
  `enable` link error on the first run, cause unknown) rolled back cleanly.
- **`impact` is lexical.** Its edges come from symbol names and import lines, so
  distance 1 or more is a lead, not proof, and a name shorter than 4 characters makes
  no edge: a file whose symbols are all that short shows nothing impacted.
- **`diagnostics` needs Postgres**, and **`explain` takes files only**, as in v0.1.0.
- **No real-model evaluation.** The corpus and `xmustard-eval` ran only with fake
  drivers; token savings and task success on real agent tasks are not measured.
- **Rust memory tests sit near their lines under load.** The debug-build index-build
  and resident-service RSS tests failed now and then in full runs on the shared build
  box and passed alone; the dirty-memory bounds (WS-FIX-06) are the strict checks.
- Runtime data files under `backend/data` are still tracked; untracking them waits on
  the owner's approval.
