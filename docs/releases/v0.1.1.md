# xMustard v0.1.1 (unreleased)

Not tagged yet. A fix release for one release-affecting bug in v0.1.0. The fix is
built on `parity/ws-fix-03`
([build plan, WS-FIX-03](../plans/2026-09-25-parity-build-plan.md#ws-fix-03--production-streaming-secret-redactor-for-evidence-capture)).

## Fixed: evidence capture is on and redacted

In v0.1.0 no production build wired a streaming secret redactor into capture. So
`POST /api/workspaces/{id}/evidence/capture` answered `503 redaction_unavailable` to
every request. As a result, Pi's built-in tool reduction, masking and compaction fell
back to Pi's own behavior, and no hook body (Claude Code, Codex, Cursor, Pi, OpenCode)
could be captured. Only the e2e build (`-tags xmustard_e2e`) captured, and its
redactor replaced one test marker.

In v0.1.1 capture is on in every build, and every capture is redacted:

- The tool output streams through the shared WS-05 secret rules (`redact.Writer`)
  before any of it reaches the spool. The retained original, its pages, search inside
  it and the projection the client receives therefore all hold the redacted text,
  with `[REDACTED:<rule>]` in place of each secret. The rules are the ones `why_failed`
  applies to command output: the token and key patterns, key-aware secret fields, and
  the literal values of the daemon's secret-named environment variables.
- The redactor streams. It holds one 128 KiB window and a 33 KiB lookahead, which is
  the longest span any rule reads. A secret split across writes is seen whole, and the
  stream is never buffered. It retains about 0.3 MiB, and about 1.2 MiB on input that
  is nothing but secrets, inside the 2 MiB capture window.
- The output of a secret path (`.ssh/`, key files, `.netrc`, `.npmrc`, `.pypirc`,
  `.dockercfg`, `.env` and `.env.*` other than templates) is refused with
  `422 secret_path` and not retained. The client keeps its own result.
- Capture still fails closed. A server without a redactor answers
  `503 redaction_unavailable`, and a redactor that fails answers
  `503 redaction_failed`. In both cases nothing is retained.

See [docs/SECURITY.md](../SECURITY.md#evidence-capture-redaction-ws-fix-03) for the
rules and their limits.

## Measured (Linux x86_64 build box, AMD Ryzen 5 3500X)

- `redact.Writer` alone (`BenchmarkWriter16MiB`, 32 KiB writes, a secret pair every
  4 KiB): 140 MB/s. `redact.Reader` measures 128 MB/s on the same input.
- The capture route, measured end to end against a real `xmustard-api`. Each figure is
  the range of three runs, compared with the same build using a pass-through
  redactor:

  | Workload | Redacted | Pass-through |
  |---|---|---|
  | 6 sequential raw 16 MiB captures, a secret pair every 4 KiB | 43.2 to 45.9 MB/s | 51.3 to 54.6 MB/s |
  | 200 Claude hook bodies of 256 KiB, 4 at a time | 79.5 to 81.5 MB/s | 101.5 to 107.0 MB/s |
  | API peak RSS (`VmHWM`) over both workloads | 37.4 to 40.0 MiB | 35.6 to 36.5 MiB |

  Idle RSS was 19.3 to 19.6 MiB for both builds.

## Compatibility

- Two new refusals: `422 secret_path` and `503 redaction_failed`. The Pi adapter keeps
  its own result for both, and does not pause capture.
- A retained original that held secrets now holds markers in their place.
  `raw_sha256` and `raw_bytes` describe the retained, redacted bytes, as before.
  `capture.body_sha256` is still the digest of the body as received.
